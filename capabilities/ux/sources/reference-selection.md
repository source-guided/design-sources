# Reference selection and user direction

References offer alternatives, not one universal visual style. Begin with the user's supplied examples, existing design system, audience, task frequency, device context, and accepted preferences. Keep those decisions in the consuming project, not the common plugin.

For a newly designed interface without an established product pattern, establish a concrete comparison basis through the relevant reference indexes. Select only the references needed for the material design questions, but do not exempt a screen merely because its data model or implementation is small. General judgment guidance and a palette name do not establish the hierarchy, control relationships, density or feedback composition of the proposed screen. Inspect relevant first-party guidance and actual rendered examples or product behavior where those relationships matter. Use an existing accepted product pattern when available. If a reference cannot be inspected, keep that comparison unavailable rather than representing its principles as an observed example.

Identify what question each reference answers and what can transfer to the current task. Compare information grouping, the relationship between explanation and next action, relative emphasis and state changes. Treat its applicability as a hypothesis to check in the new composition, not a reason to copy a component or its numerical values. A screenshot alone does not establish save/cancel, error or keyboard behavior. Conversely, a behavioral specification alone does not settle visual proportion or spacing.

When a platform or accessibility claim determines a design choice, resolve the applicable primary source and its scope. Distinguish the required user outcome from a sufficient technique, an illustrative example, a browser behavior and a product convention. Check the relevant control and access conditions before treating any of them as a compulsory treatment. Inspect the rendered implementation to establish what actually activates; do not infer behavior solely from a familiar API or class name.

Use the breadth of the catalogue selectively:
- UI reference IDs `carbon-table`, `linear-views`, and `notion-views` offer different information-density and view-selection examples.
- UX IDs `atlassian-inline`, `carbon-modal`, and `fluent-drawer` cover different editing surfaces.
- UX IDs `gov-questions`, `gov-errors`, `nng-disclosure`, and `nng-modal` cover task progression, recovery, and interaction costs.
- UX IDs `wai-dialog`, `css-focus-visible`, `wai-focus-indication`, `wai-status-messages` and `web-cls` support applicable behavior and access questions; they are not complete aesthetic prescriptions.
- The Figma reference branch explains tool/design context; actual project design files belong in the consuming project's registry.

If multiple directions materially affect the result and the user's preference is unknown, show two or three relevant alternatives with concrete tradeoffs, and ask only for that material preference. Continue independent work; do not create a mandatory approval gate at every phase. Reuse an already expressed preference instead of asking again. When the user delegates the direction, make and record the supported choice without asking for a preference that is not necessary to proceed. For a narrow fix, use the existing product direction and inspect only references needed to settle the changed question.

Record chosen reference IDs, what was adopted, what was intentionally not adopted, and the user's preference. Do not turn one product's numerical limits, brand style, or component-count recommendations into global rules. A dense expert tool, a first-time service form, and an image-led catalogue can legitimately need different layouts.

Once a direction is selected, use `visual-expression` through the UX reference index to judge its expression in the actual composition, and `workflow` for the shared decision process. Use `verification` for the relevant observations. Preference guides the choice; a generic style checklist does not establish user acceptance.

Next references: use the package design reference index, then the relevant UI or UX index. When a source suggests another source, return to the appropriate reference before reading it.
