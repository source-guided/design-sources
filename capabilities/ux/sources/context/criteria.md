# Task and design context

Treat a requested feature or page as evidence of intent, then identify the outcome the person is trying to reach. Understanding the request includes what they need to learn or accomplish and what that enables them to do next; viewing can itself complete the task. An inferred purpose must not override an explicit user choice or an adopted requirement.

- What result is the user seeking, and what do they already know? Which part of their wording names a means rather than the result?
- Which requirements and preferences came from the user or the product owner, and which choices remain open?
- What available user state, entry context, ongoing work or task constraints change the likely immediate need? Separate observed facts, explicit intent and plausible inference; consider whether the evidence is current and sufficient.
- What other purposes could reasonably explain the same request or entry? When the purpose is uncertain, what useful starting point can serve the user without prematurely committing them to one interpretation?
- Which information or preparation can the program provide from what it already knows, and which decisions genuinely require the user's intent? Identify the task-specific basis rather than assuming that every visit needs personalization or a prediction model.
- Which existing design, domain policy or data source is applicable, and what is its scope and authority? Product owners supply concrete priorities, validity conditions and thresholds; this source does not invent them.

Keep consequential purpose assumptions and their evidence with the consumer's existing decision records so another worker can understand and reconsider the design. Use the [information architecture area](../../../../references/navigation/index.json) to translate these purposes into information priority and action paths, and observations from representative use to challenge the assumptions.
